# DEVELOPMENT

## Project snapshot

- DevCloud: self-hosted browser IDE platform (FastAPI + Podman), controller plus outbound-only CPU/GPU workers, MLflow model serving.
- Source: `https://github.com/aydinguven/devcloud` (GitHub by owner's choice; not on Forgejo). Default branch `main`, latest release `v3.28.0` (`v3.18.0` was tagged but its release failed and stays a draft).
- Release process: bump `app/__init__.py` `__version__` via PR, then push tag `vX.Y.Z` on the merged `main` commit. `.github/workflows/release-platform.yml` builds the bundles, creates the GitHub Release and advances the `stable` update channel.
- Deployment: own installer/offline bundle (`INSTALL.md`, `AIRGAP.md`, `WORKERS.md`); not a Tupperware project.
- Local setup: `python -m venv .venv`, `.venv\Scripts\python -m pip install -r requirements.txt`, run `python run.py` (http://127.0.0.1:8000).
- Tests: `.venv\Scripts\python -m pytest -q`. No CI on PRs/merges; run this before every PR. The release workflow's `tests` job gates publishing.

## Decisions

- 2026-11-06 (unreleased, migration 38): AD users get GenAI access without opting in. On every successful login of an `active_directory` user, `genai.auto_provision` (called from `POST /api/auth/login`) creates or adopts the LiteLLM user (default team, budget and role from the GenAI settings) and a `GenAiAccount`. When Workspace AI points at the same LiteLLM, it also issues the per-user workspace key right away. Before, both happened only after the user pressed "GenAI erişimi oluştur".
  - It runs only when GenAI is enabled and configured and the admin switch **"AD kullanıcılarına girişte LiteLLM kullanıcısı ve workspace anahtarı otomatik oluştur"** (Admin > Entegrasyonlar > GenAI, `genai_settings.auto_provision_directory_users`) is on. Migration 38 adds the column with default on, so upgraded installs start provisioning at the next AD login unless an admin unticks it. Turning it off stops new provisioning only; existing LiteLLM users and keys stay. Local (internal) accounts are unchanged and still opt in on the GenAI tab.
  - After the workspace key exists, later logins make no LiteLLM calls; workspace creation keeps the key current (team changes, deleted keys), as before.
  - The personal key is not issued at login because it is shown only once. The GenAI tab shows "LiteLLM kullanıcınız mevcut" and the user can still create one.
  - `workspace_gateway_token` now gives a per-user key to any user with a `GenAiAccount`, not only to users with a personal key.
  - Failures are logged and never block the login; the next login retries. If LiteLLM accepts the connection but hangs, the first login can wait up to the LiteLLM timeout (default 15 s).
  - Existing AD users are provisioned at their next login. There is no bulk backfill.
  - One test added: `test_directory_login_provisions_litellm_user_and_workspace_key`.

- 2026-11-04: workspace port noise and Kilo Code's internet traffic.
  - **Ports view.** DevCloud publishes one loopback host port per workspace. The many entries came from VS Code's default `remote.autoForwardPortsSource: process`, which lists every listening socket: the Kilo agent (`kilo serve --port 0`), language servers, Jupyter kernels. The managed settings (Kilo Code and Cline, plus the image defaults) now use `output`, so a port is forwarded only when a terminal or debugger prints its URL. `/proxy/<ws>/port/<N>/` and share links go through the container bridge IP and do not depend on VS Code forwarding; manual forwards still work.
  - **Kilo telemetry.** The extension spawns its CLI with `KILO_TELEMETRY_LEVEL` from `vscode.env.isTelemetryEnabled`, overriding the image's `off`. code-server's `product.json` has `enableTelemetry: true` and it ignores the `DISABLE_TELEMETRY` env var, so the CLI ran with `all` and retried `us.i.posthog.com` every 3 s. The managed settings now set `telemetry.telemetryLevel: off`. With it, the 7.8.17 CLI made no outbound request while serving config, providers, agents, MCP, sessions and skills (checked through a logging proxy). `CONFIG_DIGEST_SALT` is v2 so Kilo Code containers are recreated once on next start; Cline containers pick it up when recreated.

- 2026-11-04 (3.28.0, PR #83): two user reports.
  - **The AI Factory tab no longer turns into the IDE.** Since a55f89b (3.26.0), the create flow ran `window.location.assign` to the IDE, replacing the dashboard tab. Now the `done` event opens the IDE with `window.open(..., "_blank")` and reloads the dashboard. Browsers can block that tab after a long deployment, because it is no longer the user's click. In that case the modal shows "IDE'yi Yeni Sekmede Aç" and "Panele Dön". The Başlat button never navigated; it still only reloads the dashboard.
  - **The Kilo Code images bake in the Python tooling.** Since 3.18.0 the image held only the AI extension; the retired `vscode-python` image had `ms-python.python` and `ms-toolsai.jupyter`, installed unpinned with `|| true`. `vscode-kilo` and `vscode-cuda` now install the list in `extensions.txt` from Open VSX, SHA-256 pinned, and fail the build if one is missing. The list: Python 2026.4.0, Python Debugger 2026.6.0 (linux-x64), Python Environments 1.40.0, basedpyright 1.40.2, Ruff 2026.92.0 (linux-x64) and Jupyter 2025.9.1 with keymap, renderers, cell tags and slideshow. Pylance is not on Open VSX, so basedpyright is the language server and `python.languageServer` is `None`, both in the image and in the settings written at start. The install loop was run against the code-server 4.137.0 binary (all 10 installed, a bad checksum fails, a missing extension fails the check). No container build was possible in the sandbox.

  - Migration 37 deletes the `placement_tags` rows of kind `datacenter` and drops `nodes.datacenter` and `workspaces.datacenter`. Migration 31 no longer seeds IDM/ODM, so a fresh install never has them. `placement_tags.kind` stays; every row is now `custom`. - 2026-11-04 (3.27.0, migration 36, PR #80): **Admin > Skill Kütüphanesi** (new admin section 07) stores single-file Agent Skills (`skills` table: name, description, content, enabled). Name and description are read from the `SKILL.md` frontmatter with PyYAML (now listed in `requirements.txt`; it was already installed through MLflow) and checked against the Agent Skills rules (name `^[a-z0-9]+(-[a-z0-9]+)*$`, at most 64 characters; description at most 1024 characters). Bundled `scripts/`, `references/` or `assets/` are not supported.
  - Delivery: the enabled skills go into one deterministic gzip tar in base64 (`app.skills.build_bundle`), sent as `ai_skills_bundle` in `container.create` for Jupyter templates and for Kilo Code templates that get a `kilo.jsonc`. The worker re-checks it with `validated_bundle`: at most 120,000 characters (one `podman run -e` argument must stay under Linux's 128 KiB `MAX_ARG_STRLEN`), at most 8 MiB unpacked, and only `<name>/` folders and `<name>/SKILL.md` regular files. The Admin API refuses a save that would push the enabled skills over the limit.
  - In the container, `DEVCLOUD_SKILLS_TGZ` is unpacked by the startup command and then unset. Jupyter unpacks into `$CLAUDE_CONFIG_DIR/skills`: claude-agent-acp 0.70.0 starts Claude Code with `settingSources: ["user", "project", "local"]`, so the Jupyter AI chat sees them as user skills. Kilo Code unpacks into `/home/coder/.devcloud/skills`, which `render_config` puts first in the `skills` list. That folder is outside the folders Kilo scans by default (`~/.kilo`, `~/.agents`, `~/.claude`), so no skill is found twice, and a folder declared in the user-level config is trusted. A failed unpack logs a line and the IDE still starts.
  - Recreation follows the CA bundle pattern: `ai_config_digest` covers the bundle only when there are skills, so this release recreates no container by itself. Start compares the stored digest with what *this* worker applies (`app.skills.MIN_AGENT_VERSION` 3.27.0). The Jupyter/VS Code start check digests only the CA bundle and the skills, never the gateway key, so it cannot rotate a key under a container that is only restarted. Known gap: `kilo.jsonc` lists the skills folder whatever the worker version, so a Kilo Code workspace on a pre-3.27 worker is recreated once without skills and again after the worker upgrade. Upgrade the workers before saving the first skill. Concurrent Admin saves are not serialized, so two parallel saves could together pass the size limit; the worker then drops the bundle.
  - No tests were added. The admin API, the 3.26 → 3.27 recreate sequence, the podman command and a `bash` run of the unpack step were checked with scratch tests that were then removed.

- 2026-11-04 (3.26.0, migration 35, PR #78): Admin > Entegrasyonlar > Workspace AI gets an optional **Gateway CA paketi** (PEM, CA-only, validated like the worker trust bundle). The LiteLLM gateways (IDMVLLMGWP1-3) serve a certificate signed by the private "LiteLLM Gateway LAB CA", which the worker's httpx (certifi) and the workspace runtimes do not trust.
  - Stored in `jupyter_ai_settings.ca_bundle_pem`. The connectivity test sends it to the worker, which adds it to httpx's default trust. `container.create` carries it as `ai_ca_bundle` for Jupyter and VS Code templates only (DevCloud owns their startup command); terminal and service templates do not get it.
  - In the container: the bundle arrives as `DEVCLOUD_CA_BUNDLE_PEM`. The startup command writes `/tmp/devcloud-ca/extra-ca.pem` and `ca-bundle.pem` (image system bundle + extra) and unsets the variable. `SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE` and `CURL_CA_BUNDLE` point at the combined file, `NODE_EXTRA_CA_CERTS` at the extra file. No image rebuild, no root, no host mount.
  - Recreation: `ai_config_digest` now covers the bundle (unchanged when no bundle is saved, so the release itself recreates nothing). Start compares the stored digest with what *this* worker applies (`CA_BUNDLE_MIN_AGENT_VERSION` 3.26.0), so a pre-3.26 worker never recreates in a loop. Jupyter and VS Code containers are recreated once after the bundle is saved or changed; files outside the mounted work directory are lost, as with Kilo Code config changes.

- 2026-11-03 (3.25.0, migration 34, PR #76): phase 2 of the Kubernetes target. Each published image release queues the Bamboo plan `AIMLOPS-RETAG` (re-tag + Jira tasks). Aydin chose:
  - `pkg.img.name` is `rfs_code/app_name:X.Y.Z` in lower case, without the registry host; `pkg.groupid` and `pkg.name` are the RFS code and app name in upper case.
  - Retry is manual only (`POST /api/mlflow/image-releases/{id}/bamboo-retry`, same permission as the release retry). No CA file field; only a TLS verification switch. The plan allows concurrent builds, so no queuing on our side.
  - `_mark_published` sets `bamboo_status=pending` in the PUBLISHED commit when the integration is enabled; `trigger_pending_bamboo_builds` in the release worker claims it (`triggering`) and records `queued` (with `buildResultKey`) or `failed`. A claim older than 120 s is marked failed, not resent, to avoid duplicate Jira tasks.
  - The request also sends `X-Atlassian-Token: no-check`, since Atlassian XSRF protection can reject form posts to REST without it.

- 2026-10-23 (3.24.0, migration 33, PR #75): upstream Kilo Code (`kilocode.kilo-code` 7.8.17, linux-x64 VSIX from Open VSX, SHA-256 pinned) replaces TCMB Code. Aydin chose:

  - **Catalog and skills are Admin fields**: the TCMB Library URL is reused as the catalog URL (root, `/mcp` refused), plus an encrypted catalog token and a skills URL list. With a catalog URL, `render_config` adds `mcp.servers.kilo-catalog` (remote `<url>/mcp`, `oauth: false`, Bearer header) and `kilo-install` (`bash /opt/kilo/LocalMCP.sh`, `CATALOG_URL`/`MCP_TOKEN`). - 2026-10-22 (3.23.0, PR #73, no schema change; spec `.kiro/specs/mlflow-kubernetes-publish/`): Kubernetes applications are self-service. Before, an admin had to create a project and then an application bound to the model before anyone could publish. Now the deploy modal takes an RFS code (select) and an app name (input), and `POST /api/mlflow/image-releases` takes `{project_id, app_name}` instead of `application_id`. An unknown name is created under `admission_transaction` and bound to the release's model. Aydin chose:

Application rows can only be disabled, rebound to another model, or deleted while they have no releases. The admin create-application endpoint is gone.
  - A new app name must start with the RFS code (`app.kubernetes_publish.app_name_fits_project`). Existing names are not re-validated.
  - The model binding is still the only publish guard: an existing application only publishes the model it is bound to. Any AD user can open a new application under any RFS code.

- 2026-10-20 (3.22.0, PR #71, migration 32; spec `.kiro/specs/mlflow-kubernetes-publish/`): the Kubernetes deploy target ends at the deploy registry. AI Factory builds the MLflow model version (or reuses a ready build), then the controller runs `skopeo copy` from the intermediate registry to `{deploy registry}/{rfs_code}/{app_name}:X.Y.Z` and records the digest. The platform team re-tags (`X.Y.Z-RC.BN` test, `X.Y.Z-BN` prod) and deploys with Helm, with secrets coming from Vault → External Secrets → `envFrom`. AI Factory never handles database credentials. Aydin chose:
  - Publishing is open to every AD user and admin for now (`app.kubernetes_publish.can_publish_images`), so it can be limited later.
  - Releases get their own tables (`mlflow_image_releases`, events) instead of extending `mlflow_deployments`; status is a plain string column.
  - The modal drops the namespace, replica and flavor inputs; the namespace comes from an admin-defined Kubernetes project (Admin > Kubernetes, new section 07).
  - After a publish, AI Factory sets `aifactory.image` and `aifactory.image_digest` tags on the MLflow model version. This is the first MLflow write; a failure there is only a warning.
  - No CA file for the deploy registry: an optional "TLS doğrulama" switch maps to `--tls-verify=false` / `--dest-tls-verify=false` (which also allows plain HTTP), and the registry test then also tries `http://`. An optional `v2s2` manifest conversion covers a registry that rejects OCI.
  - Publish-only builds are not imported into `WorkspaceImage`, so workers do not sync them. `_build_image` became `ensure_model_build(owner, import_image=...)`, shared by deployments and releases; AI Factory still requires an imported build, so it rebuilds rather than reusing a publish-only one. The three GC functions count in-progress releases as references.
  - The release loop (`image_release_service`, task "Kubernetes imaj yayın kuyruğu") is separate from the sequential deployment loop.
  - The tag is checked before the build and again before the release enters `publishing`, so `publishing` means "the tag was free and the copy began". Any failure in that state, and recovery after a restart, goes through `_settle_started_publish`. If the tag exists, the release is published, with a warning and the MLflow tags. If it does not, the release fails, or recovery requeues it. If the registry cannot be reached, the release is checked again 30 s later. A pushed tag is never left behind a failed release, which is what lets application delete remove failed releases.
  - Never-overwrite is check-then-copy, and `skopeo copy` replaces tags. Nexus "Disable redeploy" on the hosted repository is the real guarantee and is documented as a prerequisite.
  - A failed release keeps its build for 24 h (`_FAILED_RELEASE_BUILD_RETENTION`), so a retry after fixing Nexus rights or the manifest format does not rebuild. Published releases do not pin their build.
  - Users who cannot publish get no targets from `/api/mlflow/kubernetes/options`. No worker change: the build RPC is unchanged.
  - A behavioural review compared HEAD's `_build_image` with the new `ensure_model_build` in six scenarios; AI Factory behaviour is identical. The one intended difference: a previous build still used by a release is not cleaned up.

- 2026-10-15 (3.21.1, PR #68): native rootless workers had `XDG_RUNTIME_DIR=/run/user/0`. In system units, systemd's `%U` is the service manager's uid (0), not the `User=` account's. So `devcloud-worker.service` created a root-owned `/run/user/0`, and every Podman call failed with `mkdir /run/user/0/libpod: permission denied`; this was seen on IDMSYAPZET7 as image sync never loading. The unit now uses `{{UID}}`/`{{USER}}`, and `InstallerEngine._install_services` renders the service account's numeric uid (`_service_uid`, shared with `_prepare_images`). The install, repair and update plans all rewrite the unit, so updating a worker fixes it. Hosts patched by hand with a `runtime-dir.conf` drop-in get the same values and can keep it. The old string-pinning tests asserted `%U` and were replaced by one test that renders the installed unit. No schema change.

## Known issues and risks

- code-server keeps a VSIX's zip modes. The TCMB Code 7.8.3 VSIX stored `bin/` as 0664 (failed `v3.18.0`); upstream Kilo Code 7.8.17 ships 0755, and the Containerfiles still restore 0755 on the non-`.js` files in `bin/`. The Open VSX linux-x64 VSIX is pinned by SHA-256 in `containers/vscode-kilo/Containerfile` and `containers/vscode-cuda/Containerfile`.
- The failed `v3.18.0` run left a draft GitHub Release `v3.18.0`, and its successful Rocky platform job may have pushed 3.18.0 controller/worker images. Nothing points at them; the release scope ignores drafts.
- Kilo Code: the shared indexing key and the catalog token are readable by every Kilo Code user inside their workspace; restrict the indexing key to the embedding model and budget it in LiteLLM. Recreating a container on a config change resets state outside `/home/coder/project` (extra extensions, Kilo Code chat history under `~/.local/share/kilo`).
- `kilo-install`'s `open_catalog` needs a browser opener (`$BROWSER`, `xdg-open`, ...) in the container; the image installs none, so unless the agent inherits code-server's `BROWSER` helper it returns the catalog page URL for the user to open. Not checked in a running workspace. `install_items` works headless.
- After the 3.24.0 update a `vscode-cuda` worker still holds the old TCMB Code image under the same tag until the new one is loaded. Kilo Code recreates are gated on the pinned checksum being reported by the worker, but the worker itself only runs `podman image exists <tag>`. The "image not synced yet" notice on a kept container is only logged (like the outdated-worker notice).
- The `kilo-code.new.model.*` settings (also in upstream 7.8.17's `package.json`) and the global config were verified with TCMB Code in a running `vscode-tcmb-3.18.1` container on 2026-10-14 (CI probe): the agent loads the file and the picker shows the configured default model. `KILO_DISABLE_MODELS_FETCH` does not stop the agent fetching Kilo's model list and marketplace from `api.kilo.ai`; offline this should only fail, but check for start-up delays on IDMVAIFACT1.
- In Restricted Mode VS Code disables Kilo Code entirely (the extension declares no `untrustedWorkspaces` support); users must trust `/home/coder/project`.
- The agent rewrites `~/.config/kilo/kilo.jsonc` on first run (adds `permission.bash: allow`, pretty-prints) and on settings changes in its UI; DevCloud overwrites it on every container start, so UI-made global settings do not survive a restart.
- Workspace snapshots (all-in-one only) of a Kilo Code workspace become a plain `vscode` custom template, which gets the legacy Cline wiring instead of Kilo Code, and `podman commit` captures the rendered `~/.config/kilo/kilo.jsonc` with its keys (Cline's `secrets.json` had the same exposure). Not addressed.
- `requirements.txt` uses open ranges. SQLAlchemy 2.1 no longer installs `greenlet`, which broke CI and the release build's pytest step (both since removed; the release workflow's `tests` job is now the test gate) on 2026-09-29; fixed by requiring `sqlalchemy[asyncio]`. Other packages can still drift on a fresh install; consider exact pins or a constraints file.
- The deployment background worker processes jobs one at a time, so a long image-sync wait delays other queued deployments. This was already the case during image builds.
- `tests/test_mlflow_model_build.py::test_worker_unit_exposes_the_virtualenv_console_scripts_on_path` fails on Windows only (it asserts `os.sep` inside a Linux unit file).
